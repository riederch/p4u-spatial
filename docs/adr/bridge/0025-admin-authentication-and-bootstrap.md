# ADR 0025: Bridge Administrator Authentication and First-Run Bootstrap

Status: Accepted

Date: 2026-09-21

## Historical note

No original ADR for Bridge administrator authentication remains available. This ADR reconstructs
and establishes the current intended security architecture from the implemented services and
administrator-authentication documentation.

## Context

The Bridge has a privileged web/API administration surface for device authorization, credentials,
configuration and other security-sensitive operations.

A fresh Bridge installation also needs a safe way to create the first administrator without
requiring a permanent deployment secret as the normal login mechanism.

## Decision

Bridge administration uses persistent administrator identities with one or both of two independent
permanent authentication methods:

1. WebAuthn passkeys,
2. username + password + TOTP.

Password alone is never a valid administrator authentication method.

### Passkeys

- Passkeys require user verification.
- The Bridge stores public credential material/counters, not authenticator private keys.
- WebAuthn is bound to configured stable RP ID and origin.
- An administrator may register multiple passkeys.
- The final passkey may only be removed when another valid permanent login method remains.

### Password + TOTP

- Password and a valid TOTP code are both required.
- Passwords are stored using salted password hashing.
- TOTP enrollment is not activated until a valid TOTP confirmation completes.
- Password + TOTP may coexist with passkeys.

### Browser sessions

Successful login creates a server-side administrator session.

Browser sessions use a secure HttpOnly session cookie. State-changing session-authenticated
requests require a matching CSRF token.

Disabling an administrator invalidates that administrator's active sessions.

### First-run bootstrap

When no usable administrator exists, the Bridge generates a one-time setup proof and exposes setup
through the web flow.

The proof is generated by the Bridge, is not a normal long-lived deployment configuration value,
and is consumed once permanent administrator authentication is configured.

A deployment-level administrator key may remain as an explicitly configured compatibility/recovery
mechanism, but it is not the target normal browser authentication path and MUST NOT replace
per-user administrator identities.

## Consequences

- Normal administration does not depend on one shared permanent password or deployment secret.
- Passkeys can be the primary passwordless method while password + TOTP remains an independent
  alternative.
- First-run setup works in Docker/Home Assistant without pre-provisioning a permanent admin key.
- Stable public origin/RP configuration is required for WebAuthn.
- Server-side administrator session state and CSRF protection are part of the Bridge trust boundary.

## Implementation anchors

- `docs/admin-gui-auth.md` — administrator authentication model and browser security semantics.
- `bridge/src/services/admin-passkey-service.ts` — WebAuthn registration/authentication and passkey lifecycle.
- `bridge/src/services/admin-password-totp-service.ts` — password hashing, TOTP setup and combined verification.
- `bridge/src/services/admin-session-service.ts` — server-side administrator sessions and CSRF token binding.
- `bridge/src/services/setup-bootstrap-service.ts` — one-time first-run setup proof.
- `bridge/src/server.ts` — authentication enforcement, cookies, CSRF and compatibility admin-key path.
