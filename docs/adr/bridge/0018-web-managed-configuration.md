# ADR 0018: Web-Managed Bridge Configuration

Status: Accepted

## Context

P4U Spatial Bridge must be deployable independently of Home Assistant. Home Assistant is a packaging and lifecycle environment, not a source of bridge-specific behavior or configuration semantics.

The current implementation still reads a substantial part of its functional configuration from `P4U_*` environment variables, and the Home Assistant app maps add-on options into those variables. That is a transitional implementation state, not the target architecture.

## Decision

All operator-facing P4U Spatial application configuration is owned by the Bridge and managed through the Bridge web interface.

The Bridge persists this configuration in its own durable state. The same persisted configuration model is used regardless of whether the Bridge runs:

- directly as a Node service,
- in a generic Docker container,
- as a Home Assistant app,
- or under another supervisor.

Home Assistant, Docker Compose and other deployment wrappers MUST NOT define a second functional configuration model.

### Web-managed configuration

The web interface is the authoritative configuration surface for, at minimum:

- administrator/security setup,
- source title and source behavior,
- repository provider and repository profile,
- Git remote URL, branch and credentials,
- RCHKB projection root and write policy,
- federation routes, upstream URLs and credentials,
- Spatial write policy,
- session and pairing lifetimes,
- scan upload limits and staging retention,
- XR application release/update settings,
- and future operator-facing feature settings.

Credentials entered through the web interface remain server-side and MUST NOT be exposed to XR clients.

### Deployment bootstrap is not application configuration

A deployment environment may provide only values that are required before the web application can start and therefore cannot be configured from that same web application.

Packaged deployments SHOULD minimize this bootstrap surface. In particular:

- the Bridge listens on its documented internal port;
- Docker or Home Assistant performs external port mapping;
- packaged persistent state is mounted at a documented fixed path;
- functional behavior MUST NOT depend on Home Assistant options or Docker-only environment variables.

No new `P4U_*` environment variable may be introduced for operator-facing functional configuration.

### First-run administration

A fresh Bridge installation enters setup mode when no administrator identity exists in persisted state.

Initial administrator setup MUST be completed through the web interface. Any one-time bootstrap proof needed to protect first setup is generated by the Bridge itself, is not a long-lived deployment setting, and becomes invalid after successful setup.

The target architecture therefore does not require a permanent `P4U_ADMIN_KEY` environment variable.

### Deployment parity

The Home Assistant app and a generic Docker deployment execute the same Bridge application artifact.

The Home Assistant layer may provide:

- process lifecycle,
- image packaging,
- persistent volume mapping,
- network exposure,
- supervisor integration,
- and ingress/proxy integration.

It MUST NOT contain repository, federation, XR, Spatial, RCHKB or other Bridge business logic.

## Consequences

- A Bridge can be moved between Docker and Home Assistant without translating functional configuration models.
- Configuration backup and migration become part of Bridge state rather than deployment metadata.
- The Home Assistant app can eventually remove its functional `options` / `schema` entries.
- The generic Docker image does not need a parallel set of application environment variables.
- Changes to settings that require rebuilding runtime services may be persisted through the GUI and applied through a controlled Bridge restart until live reconfiguration exists.
- The current environment-variable configuration remains a migration gap and must not be expanded.

## Implementation anchors

- `bridge/src/services/bridge-config-store.ts` — persisted operator configuration and one-time migration from bootstrap values.
- `bridge/src/main.ts` — loads bootstrap values once, migrates/loads Bridge-owned persisted configuration, then constructs runtime services from it.
- `bridge/src/web/admin-page.ts` — operator-facing Bridge configuration UI.
- `bridge/src/config.ts` — transitional environment/bootstrap compatibility layer; this remains a documented migration gap rather than a second target configuration authority.

## Reconciliation note

As of 2026-09-21 the target architecture is only partially migrated: `config.ts` still accepts legacy
functional `P4U_*` values as first-run/bootstrap migration input. The persisted `BridgeConfigStore`
is authoritative after migration. New functional environment variables remain prohibited.
